● Declaration Model (Representation #4)

  The Declaration Model is the first normalized, typed IR that the compiler
  owns. It takes the 13 raw extraction surfaces (stringly-typed JSON) and
  converts them into validated Rust types with typed enums, provenance tracking,
   and explicit error handling.

  Core Structure

  Defined in crates/regseq-model/src/declaration/mod.rs:

  pub struct DeclarationModel {
      pub driver: DriverDecl,                      // Driver identity (name, 
  compatible, bus, class)
      pub resources: ResourceDeclSet,              // MMIO, interrupts, clock, 
  reset, pinctrl
      pub synchronization: SynchronizationDeclSet, // Locks, completions, guards
      pub callbacks: CallbackDeclSet,              // Trait impl declarations
      pub registers: RegisterDeclSet,              // Register blocks, 
  descriptors, ops
      pub properties: PropertyDeclSet,             // Firmware properties
      pub timed_delay: TimedDelayDeclSet,          // Delay intrinsics & 
  duration ctors
      pub logging: LoggingDeclSet,                 // Log call sites
      pub pm_gate: PmGateDeclSet,                  // Power management gates
      pub bodies: BodyDeclSet,                     // Legacy HIR-style bodies 
  (stubs)
      pub mir_bodies: MirBodyDeclSet,              // Canonical MIR bodies (CFG 
  form)
      pub build_context: DeclarationBuildContext,   // Build metadata
  }

  What Normalization Does (#3 → #4)

  Implemented in crates/regseq-model/src/declaration/normalize.rs. Each of the
  13 raw families is normalized independently:

  1. Stringly-typed tags → typed enums: "mutex" → SyncFieldKind::Mutex,
  "serial_uart" → DeviceClass::SerialUart, "read_raw" → WrapperMethod::ReadRaw,
  etc.
  2. Validation with explicit errors: Unrecognized tags produce
  NormalizeError::UnrecognizedTag { family, field, value } — no silent defaults.
  3. Provenance tracking: Every entity gets a Provenance record (which raw
  family, which containing function, optional source path).
  4. Absent families → empty sets: Missing raw sections become empty
  collections, never synthesized placeholders.
  5. Deterministic & locally scoped: Each family normalizes independently, no
  cross-family or binding-layer logic.

  What It Captures vs. What It Doesn't

  Captures:
  - Field-level identity (names, IDs, types) with typed classification
  - Method/function evidence (which functions call what operations)
  - Call-site provenance (containing_fn)
  - Structured register configuration (offsets, widths, named values)
  - Function bodies in MIR/CFG form with local decls and basic blocks

  Honestly does NOT capture (by design):
  - Binding targets — register wrapper call sites carry the method but not which
   register they target (that's a Layer 2 / join job)
  - Platform binding data — interrupt binding hints stay opaque in a sidecar
  - Cross-entity relationships — no join logic, no resource resolution

  Purpose

  The Declaration Model is the boundary where the compiler takes ownership of 
  the data. Upstream, the extraction surfaces are driver-extracted JSON with
  string tags. Downstream, everything operates on typed, validated Rust
  structures. It answers: "What does this driver spec declare?" — without yet
  asking "How does it bind to a platform?" (that's representation #5–6).

● Extraction Surfaces (Representation #3) — Deep Analysis

  The Extraction Surfaces are 13 independent facets of driver information
  extracted from rustc's HIR/MIR during the after_analysis compiler callback.
  Each surface captures a specific cross-cutting concern, and they're combined
  into a single RawFrontendArtifact JSON file.

  Orchestration

  Entry point: crates/regseq-driver/src/callbacks.rs (the after_analysis
  callback)

  Surfaces are extracted in dependency order (e.g., interrupts before
  synchronization, because sync needs ISR handler names for legality checks).
  The result is serialized to {output_dir}/drivers/{driver_name}.raw.json.

  ---
  The 13 Surfaces

  1. Driver Identity (extract/driver_identity.rs)

  Parses #[rseq::driver(...)] and #[rseq::device_class(...)] attributes via
  token-tree parsing.
  - driver_name, compatible strings, device_class, optional bus
  (integrated/amba/pci)

  2. Register Access (extract/register_access.rs)

  The largest surface. Captures register-block structure, MMIO fields, wrapper
  call sites, poll sites, and register bitfield descriptors.
  - Register blocks: fields with #[rseq::register(...)] attributes
  (access_width, endian, side_effects, byte_offset, access_kind)
  - MMIO fields: Mmio<T> typed fields with #[rseq::mmio(id = "...")]
  - Wrapper call sites: .read(), .write(), .modify(), .set(), .read_raw() calls
  + containing function
  - Poll call sites: poll::until(...) invocations
  - Register descriptors: bitfield macro patterns with offset, width, named
  values

  3. Trait Callbacks (extract/traits.rs)

  Finds impl Trait for DriverType blocks for the four supported traits:
  - Lifecycle (context: Framework): init, deinit
  - Serial (context: SubsystemSerialized): port_open, port_close, configure,
  tx_byte, rx_char, tx_ready, tx_empty, flush_rx_fifo, flush_tx_fifo, send_break
  - SerialConsole (context: SubsystemSerialized): console_write
  - PowerManagement (context: Framework): suspend, resume

  Validates method signatures (receiver, parameter types, return types).

  4. Firmware Properties (extract/property.rs)

  Scans fields with #[rseq::property(id = "...")]:
  - field_name, field_type, property_id, default_literal, vendor_prefix
  - required: bool — T = required, Option<T> = optional
  - Lint: flags required fields that also have defaults

  5. Clock Resources (extract/clock.rs)

  - Fields: Clock / Option<Clock> with #[rseq::clock(id = "...")]
  - Call sites: .enable(), .disable(), .get_rate() + containing function

  6. Reset Resources (extract/reset.rs)

  - Fields: ResetLine / Option<ResetLine>
  - Call sites: .assert(), .deassert(), .toggle(duration) — validates Duration
  arg for toggle

  7. Pin Control (extract/pinctrl.rs)

  - Fields: PinCtrl / Option<PinCtrl> with optional #[rseq::pinctrl(id = "...")]
  - Call sites: .apply::<StateType>() — extracts turbofish type argument

  8. Interrupt Resources (extract/interrupts.rs)

  - Resources: Interrupt / Option<Interrupt> / [Interrupt; N] with
  #[rseq::interrupt(id = "...")] + layer-2 hints (trigger_type, polarity,
  priority, shared)
  - ISR bindings: methods with #[rseq::isr] or #[rseq::isr(field_name)],
  validates IrqResult return type, checks for index param on array bindings

  9. Synchronization (extract/synchronization.rs)

  - Fields: Mutex<T>, SpinLock<T>, IrqSpinLock<T>, Completion
  - Lock operations: .lock() call sites
  - Completion operations: .wait(), .signal(), .reset()
  - Guard scopes: one per lock operation
  - ISR legality: non-ISR-safe locks in handler context = error,
  Completion::wait() in ISR = error

  10. Timed Delay (extract/timed_delay.rs)

  - Delay call sites: busy_wait or sleep (canonical vs compatibility paths)
  - Duration constructors: Duration::from_us/from_ms/from_s
  - Legality: sleep in handler context = error

  11. Diagnostic Logging (extract/logging.rs)

  - Call sites: error/warn/info/debug with level, template string, arg count,
  and typed arg kinds (13 primitive variants: u8–u64, i8–i64, usize, isize,
  bool, str, ptr)
  - Validates placeholder count matches arg count, validates format specifiers

  12. PM Gate (extract/pm.rs)

  - #[rseq::pm(idle = ..., wakeup_capable = ...)] on driver struct
  - Cross-validates that impl PowerManagement exists if gate is declared

  13A. Identity Enrichment (extract/identity_enrichment.rs)

  The structural backbone — provides the item hierarchy:
  - Modules: canonical path, name, child items
  - Structs: canonical path, fields with RseqFieldKind classification (Resource,
   RegisterBlock, Mmio, Property, Clock, Reset, PinCtrl, Interrupt,
  SyncPrimitive, Other), is_driver flag
  - Enums, impl blocks, free functions: canonical paths, methods, ISR markers
  - Field classification uses HIR attributes (#[rseq::*]), not type-name string
  matching

  13B. Body Surface (extract/body.rs)

  MIR function bodies extracted via tcx.optimized_mir() — CFG form with basic
  blocks and local declarations.

  ---
  How Extraction Works (rustc APIs)

  All surfaces use the same core pattern:
  - TyCtxt::hir_free_items() to iterate crate-level items
  - TyCtxt::hir_attrs() to read #[rseq::*] attributes, parsed via token-tree
  traversal
  - TyCtxt::typeck() and TypeckResults::expr_ty() for type-checked expression
  types
  - rustc_hir::intravisit::Visitor trait to walk expression trees and collect
  call sites
  - TyCtxt::def_path_str() for canonical paths

  The key design: attributes drive classification (not type-name string
  matching), and call-site evidence is always anchored to a containing function.

  Serialization

  All surface types have Raw* counterparts that convert Rust enums to strings
  and implement Serialize/Deserialize. The artifact is written as pretty-printed
   JSON with #[serde(skip_serializing_if = "Option::is_none")] for absent
  surfaces.

  Remediation Status

  Per docs/validation/01-pl011/, all 12 extraction check suites are clean — no
  open findings remain at the source-to-extraction boundary.

  What's Notably Absent

  - No receiver/target identity — a WrapperCallSite records that Read was called
   in init, but not which register was read. The register access surface
  comments explicitly acknowledge this: the raw artifact does not preserve the
  concrete target register. That resolution is a join-time (Layer 2) job.
  - No source spans — no line numbers or byte offsets.
  - No ordering — multiple call sites in the same function are collected as a
  flat Vec, with no intra-function sequencing.
  - No argument values — except logging (which captures template + typed arg
  kinds) and pinctrl (which captures the turbofish type).

  The call site representation is deliberately existence evidence — "this method
   was called somewhere in this function" — not a procedural trace. The
  procedural detail lives in the MIR bodies (surface 13B), not in the
  per-surface call site records.

❯ Now the question is what are the design choices we have for specifying user   
  data?                                                                         

● The core tension is that the compiler owns struct initialization (to wire up
  resources via OS mechanisms), so it needs a deterministic value for every
  field at construction time. Here are the options:

  1. Require Default bound — User data fields must be types implementing
  Default. The compiler emits Default::default() for each. Simple, but limits to
   types with a natural default.
  2. Attribute-specified initial value — Something like #[rseq::init(expr)]
  where the author provides a const expression. Explicit, but adds another
  attribute and the compiler must validate the expression is const-evaluable.
  3. Wrap in Option<T>, initialized to None — Author sets them during init(). No
   new mechanism needed, but forces an Option wrapper on every user field and
  .unwrap() everywhere after init.
  4. Dedicated init callback — A separate method like fn init_user_data(&mut 
  self) that runs after resources are wired but before init(). Clean separation,
   but adds a new lifecycle phase.
  5. Ban user data entirely — Everything goes through resources or properties.
  If you need local state, it lives in a resource type. Simplest for the
  compiler, most restrictive for spec authors.
  6. Zero-initialization — User data fields are zero-initialized (like C). Only
  works for primitive-like types and is semantically questionable for many Rust
  types.

  Options 1 and 3 require no new spec-level mechanisms. Option 4 is the cleanest
   if user data needs complex initialization that depends on resource/property
  values. Option 2 is the most explicit.

  What kinds of user data have you seen spec authors actually needing?

❯ Now I'm also thinking about how to clean up user data if it requires Drop     

● That's a key question. The same ownership tension applies symmetrically — if
  the compiler owns construction, it likely owns destruction too, and needs to
  know how to tear down user data.

  The options mirror initialization:

  - Default bound (option 1) — Drop is automatic if the type implements Drop.
  The compiler just drops the field in its generated teardown. Clean.
  - Option<T> wrapper (option 3) — Author can .take() in deinit() to explicitly
  clean up, or the compiler drops the Option<T> which drops the inner value.
  Also clean.
  - Dedicated cleanup callback (option 4 mirror) — Something like fn 
  cleanup_user_data(&mut self) running after deinit() but before the compiler
  tears down resources. Symmetric with the init callback.
  - Ban (option 5) — No problem to solve.

  The tricky case is ordering — if user data cleanup depends on resources still
  being alive (e.g., flushing something over MMIO before teardown), then cleanup
   must run before resource teardown. But if the compiler owns the destruction
  sequence, it controls that ordering.

  This actually pushes toward either:
  - Option 3 (Option<T>) — the author explicitly manages lifetime in
  init()/deinit(), and the compiler doesn't need to know anything special
  - Option 5 (ban) — sidestep entirely

  Do you have cases where user data would need cleanup that depends on live
  resources?

❯ user data cannot depend on live resources                                     

● That simplifies things significantly. If user data can't depend on live
  resources, then:

  - Init order doesn't matter — user data can be initialized before or after
  resources
  - Drop order doesn't matter — the compiler can drop user data at any point in
  teardown
  - No lifecycle callbacks needed — no init_user_data / cleanup_user_data phase

  This makes option 1 (Default bound) the cleanest choice. The compiler calls
  Default::default() at construction, and Rust's normal Drop handles teardown.
  No new spec-level mechanisms, no Option wrapping, no ordering constraints.

  The only limitation is that the author can't initialize user data based on
  property values or other runtime state — but since user data can't depend on
  resources anyway, Default seems like a natural fit for that kind of
  independent state.

❯ how would Rust's normal Drop be handled?                                      

● Right — this is a compiler that emits C. There is no Rust runtime. So "Rust's
  normal Drop" doesn't exist at the output level.

  The compiler would need to:
  1. Detect that a user data type implements Drop
  2. Extract/lower the Drop::drop() body to C (via MIR, like any other body)
  3. Emit the C equivalent in the teardown path
  4. Handle nested drops (fields of the user data type that themselves implement
   Drop)

  That's a lot of machinery for user data that by definition can't depend on
  resources. It essentially means the compiler must support lowering arbitrary

● Let's look at what we're dealing with. There are two related but distinct
  things:

  Register Descriptors (register_bitfields! expansion) — each one (e.g., DR_REG)
   defines the bitfield structure of a single register:

  A) Treat them as specialized module item kinds under Section 3 (alongside type
   definitions):
  - 3.4a Register Descriptors
  - 3.4b Register Blocks

  B) Treat them as part of the MMIO resource representation in Section 4.2 — the
   MMIO resource owns its register block which owns its descriptors.

  The problem

  The model has many cross-references:
  - MMIO resource → register block
  - Register block field → register descriptor
  - ISR handler → interrupt resource
  - Bodies → fields on self (resources, properties, user data)
  - Bodies → free functions, associated constants
  - Modules → sub-modules

  Each needs a stable, unambiguous way to refer to the target.

  Standard approaches

  1. Canonical path strings — e.g., "crate::registers::Pl011Registers::dr".
  Human-readable but slow to compare, fragile under renaming, and the
  string-matching pattern your project explicitly avoids.

  2. Flat interned IDs (rustc's DefId) — A single u32 index into a global table.
   Fast and compact but untyped — a function ID and a register block ID are the
  same type, so invalid references aren't caught at compile time.

  3. Typed arena indices (cranelift, rust-analyzer style) — Each entity kind
  gets its own ID type:
  struct ModuleId(u32);
  struct FunctionId(u32);
  struct RegisterBlockId(u32);
  struct RegisterDescriptorId(u32);
  struct ResourceId(u32);
  ...

  MMIO resource holds a RegisterBlockId — you can't accidentally put a
  FunctionId there.

  Approach 3 (typed arena indices) is the standard choice for modern compiler
  IRs with a well-defined entity taxonomy — which is exactly what the Regseq
  Model is. Benefits:

  compiler itself
  - Cheap — u32 copy, compare, hash
  - Stable across phases — an ID assigned in Phase 1 stays valid in Phase 2
  - Lookup efficiency — direct index into a Vec, O(1)
  - Debuggable — a side table maps each ID to its human-readable name/path for
  error messages and diagnostics

❯ let's discuss type representation                                             

● Types appear throughout the model — constants, function signatures, locals,
  fields, expressions. The question is: what type system does the Regseq Model
  need?

  What it's NOT

  It's not Rust's type system. We don't need lifetimes, trait bounds, associated
   types, or generic polymorphism. The model targets C output.

  What types actually appear in PL011

  Looking at the spec, the types that show up are:

  Primitives: u8, u16, u32, u64, bool, () (unit/void)

  Regseq domain types:
  - Resource types: Clock, ResetLine, PinCtrl, Interrupt, Mmio<T>
  - Register access types: ReadWrite<u32, R>, ReadOnly<u32, R>, WriteOnly<u32, 
  R>, Reserved<u32>
  - Framework types: RegseqError, RxChar, SerialConfig, ErrorKind, Field<u32, 
  R>, FieldValue<u32, R>, Duration, IrqResult

  Generic wrappers: Option<T>, Result<T, E>

  Compound types: [T; N] (arrays), &[u8] (slices), &mut self / &self

  User-defined types: Pl011Registers, DefaultState, SleepState, register
  descriptor types (DR_REG::Register, etc.)

  Design question

  There's a spectrum:

  1. Minimal (Cranelift-style): Just scalars and pointers. Everything else is
  opaque. Simple but loses semantic information.
  2. Domain-aware: Primitives + Regseq-specific types as first-class (resource
  types, register types, Option, Result). Analyses can reason about them.
  Backends know how to lower each one.
  3. Full mirror: Carry Rust's type representation forward. Maximum fidelity but
   unnecessary complexity.

  I'd recommend option 2 — a domain-aware type representation where:

  - Primitives are their own variants
  - Regseq constructs (resources, registers) are typed with references back to
  the identity scheme (e.g., a register field's type carries its
  RegisterDescriptorId)
  - Option<T> and Result<T, E> are explicit type constructors (not generic — the
   model knows what they are and how to lower them)
  - User-defined types reference their TypeDefId
  - Framework types (RegseqError, RxChar, etc.) have their own variants —
  they're known types with known lowering

  This avoids both extremes: the model knows enough to make semantic decisions,
  without carrying Rust's full type machinery.
