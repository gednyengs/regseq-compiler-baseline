# Linux backend — the per-OS lowering spec

This directory is the **Linux lowering-semantics spec** for the five in-scope
Regseq constructs — complete as a *per-construct lowering and scaffold*
specification, **not** a freestanding backend implementation contract. It is the
per-OS realization of the OS-neutral foundation in
[`../backend-lowering/`](../backend-lowering/README.md): that directory defines
the method (the four dispositions, the primitive census, the
agnostic-core/OS-shell seam); this directory *executes* that method against one
pinned target — **Linux mainline LTS 6.6+**.

**Scope boundary (load-bearing).** What this directory specifies is the **Linux
delta**: what each construct's primitives become, where they live in the kernel
scaffold, and how the constructs compose. What it does **not** re-specify is the
whole-model fold a real backend must perform — iterating `RegseqModel`'s
instances/types/signatures/consts/domain-attrs/lifecycle tables into a
translation unit via the multi-bank assembly (name tables, ABI/type layout,
helper-demand tracking, statics/consts recovery, the body bank, entry
classification, the errno adapter). For that fold, `generic_c` is the
**authoritative reference lowering** — semantics, emission ordering, construct
coverage, fold structure
([`../backend-lowering/agnostic-core-vs-os-shell.md`](../backend-lowering/agnostic-core-vs-os-shell.md),
[`../backend-lowering/regseqmodel-input-contract.md`](../backend-lowering/regseqmodel-input-contract.md);
as-built: `emit_generic_c_inner` `generic_c/mod.rs:237`, bank 5 `mod.rs:2276`).
Under the ratified backend contract
([`linux-open-questions.md`](./linux-open-questions.md) **§F.1**), the Linux
implementation **lowers RegseqModel directly**, consulting `generic_c` as that
reference while **owning its own emission shape** (OS include sets,
type/declaration ordering, scaffolding idiom — the output must read as a native
Linux driver). **No seam refactor of `generic_c` is prerequisite**;
shared-machinery extraction is an optional later evaluation, only after at
least two OS backends exist (the `linux-scaffold-and-dispatch.md` §8 site table
remains the candidate parameterization list if that day comes).

It is grounded in two things and only two things: (1) the **as-built** reference
backend `generic_c` (`crates/regseq-backends/src/generic_c/`), which is a *host
model* and the reference lowering; and (2) the **vendored stock kernel drivers**
under `reference-drivers/{pl011,e1000}/linux/`, which are authoritative as-built
Linux C. Every normative claim cites a repo `path:line` or a v6.6-pinned kernel
reference per the citation-discipline rules below. Where `generic_c` lowers
nothing (`poll_until`, `BarType::Io`,
`ClassTag`, `UserDataField`), the Linux spec says so explicitly and does **not**
invent a lowering.

## Scope

**In scope — exactly five constructs:**

1. **register-access** — the five MMIO ops, `poll_until`, the `map_region`
   keystone seam.
2. **bus-resource-management** — `register_driver`, the four managed preamble
   ops, config-space intrinsics, the `MmioBinding` / `BusType` / `BarType` model.
3. **device-lifecycle** — the five callbacks, the four scenarios, the managed
   steps, the typed match set, the container morph.
4. **diagnostics-logging** — the four log levels and their template lowering.
5. **RegseqError** — the framework marker, the nine-variant errno taxonomy, the
   exit-adapter boundary, and its hard separation from native OS errors.

**Out of scope:** interrupts, DMA, serial / data-path. (Out-of-scope facts —
e.g. the `dma_present` bit gating `set_bus_master` — appear only as a gate
input, never as a lowered primitive.)

This is the **lowering-semantics** spec. The complementary *artifact-shape*
discussion (generated file layout, out-of-tree vs in-tree packaging, the
regenerate/build/fix loop) lives in [`../linux-codegen/`](../linux-codegen/README.md);
the two are designed to compose — this directory says *what each construct
becomes*, that one says *where the generated bytes land*.

## The two facts to internalize first (inherited, and load-bearing on Linux)

**1. The cross-construct composition is real.** The constructs do not lower in
isolation. `generic_c` orders the bus preamble **inside** lifecycle synthesis —
`enable_device → claim_regions → set_bus_master → get_resource_handle →
map_region` (`body_emit.rs:5197-5285`) — and register-access's `map_region`
**consumes** the BRM-resolved `(base,size)`. On Linux that ordered sequence
becomes the body of `.probe()`; only `register_driver` is hoisted out to module
init. Swapping the host `(base,size)` literal for a real `pci_resource_start` /
`platform_get_resource` changes **no** register-access op (invariant **I04**,
`prelude.rs:160-162`) — that decoupling is exactly what makes the seam portable,
and it is the single fact a Linux backend must never break by reordering the
preamble or lowering a primitive standalone.

**2. Authored `RegseqError` is a different channel from native OS failures.** On
Linux both surface as a negative errno from `.probe()`, but they must not be
conflated: an authored `RegseqError` from `on_init` crosses the errno
exit-adapter (`return -EINVAL;`); a compiler-generated preamble call's native
status (`-EPROBE_DEFER`, `-ENODEV`, `IS_ERR(...)`) propagates **directly** and is
never wrapped. The boundary is the authored/generated code split, not a syntactic
one. Conflating them breaks probe deferral and erases platform semantics.

## Citation discipline

Every normative claim cites one of the following two forms (and nothing
weaker):

1. **Repo `path:line`** — into this repo's crates, docs, or the vendored stock
   drivers (cited by repo-relative path,
   `reference-drivers/{pl011,e1000}/linux/<file>:line`), which are
   authoritative as-built Linux C.
2. **A pinned kernel URL** — of the form
   `https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git/plain/<path>?h=v6.6`
   (source) or `https://docs.kernel.org/<page>.html` (documentation). These are
   **pinned canonical locations, not fetched anchors** — live fetching of
   kernel.org was not permitted in the authoring session. Every macro-level and
   usage claim backed by a URL without a line range carries an additional
   in-repo vendored-driver citation; claims whose exact upstream line matters
   (platform `.remove`/`.remove_new`, `pci_read_config_*`/`pci_write_config_*`,
   `dev_printk.h`) cite the URL with line ranges, as verified by the external
   review.

(Earlier drafts used symbolic `[L:<path>]` / `[L:doc:<page>]` shorthand and
bare vendored-driver file names; both were normalized away in the round-2
review — symbolic refs expanded to their pinned URLs, vendored cites to
repo-relative paths.)

A `generic_c` `none` (the model recognizes a primitive but the reference lowers
nothing) is a deliberate fact, never an omission — it produces a
`recognized-not-lowered` / `needs-new-surface` disposition, not an invented
Linux call.

## Target pin

**Linux mainline LTS 6.6+**, meaning: **v6.6 is the API baseline every pinned
URL cites, and the generated source must remain valid on every kernel from
v6.6 through current mainline** — where an in-range API changed, the spec pins
an explicit `LINUX_VERSION_CODE` gate rather than a single-version form
(currently one such site: the platform teardown slot, `.remove_new` below
`KERNEL_VERSION(6, 11, 0)` vs void `.remove` from v6.11 on — resolved in
[`linux-open-questions.md`](./linux-open-questions.md) C-3). The single most
consequential sub-pin is **PCI vs
platform/DT**, which changes the realization of half the BRM and register-access
rows. Version-sensitive choices (`readl` vs `ioread32`; `pcim_*`/`devm_*` vs bare
`pci_*`) are flagged as open questions in
[`linux-open-questions.md`](./linux-open-questions.md) rather than silently
resolved.
