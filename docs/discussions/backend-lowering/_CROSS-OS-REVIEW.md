# Cross-OS consistency review

Reviewed scope: the comparison is limited to register-access, bus-resource-management, device-lifecycle, diagnostics-logging, and RegseqError, which is the shared foundation scope and the stated Linux/Zephyr scope (`docs/discussions/backend-lowering/README.md:20`, `docs/discussions/backend-lowering/README.md:38`; `docs/discussions/linux-backend/README.md:42`, `docs/discussions/linux-backend/README.md:58`; `docs/discussions/zephyr-backend/README.md:28`, `docs/discussions/zephyr-backend/README.md:39`).

Verdict: the Linux and Zephyr specs mostly agree on the shared agnostic core and input contract: both treat `generic_c`'s multi-bank assembly, body spine, domain-intrinsic recognition, lifecycle ordering, entry classification, and RegseqError discriminant/switch mechanism as the shared structure, with OS-specific materialization substituted at the host-hook/scaffold/return-convention sites (`docs/discussions/backend-lowering/agnostic-core-vs-os-shell.md:3`, `docs/discussions/backend-lowering/agnostic-core-vs-os-shell.md:31`; `docs/discussions/linux-backend/README.md:12`, `docs/discussions/linux-backend/README.md:28`; `docs/discussions/zephyr-backend/zephyr-scaffold-and-dispatch.md:297`, `docs/discussions/zephyr-backend/zephyr-scaffold-and-dispatch.md:322`).

The remaining problems are not "Linux vs Zephyr cannot agree"; they are stale shared-foundation/status text, one Zephyr PCIe ordering exception that still needs explicit ratification, and inconsistent status/citation hygiene (`docs/discussions/backend-lowering/_STATUS.md:12`, `docs/discussions/backend-lowering/_STATUS.md:24`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:58`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:70`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:187`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:194`).

## Findings

### F1. Zephyr PCIe order is a pending inconsistency until ratified

Classification: real semantic divergence, not automatically OS-specific, because the shared core requires canonical ordering while Zephyr records a PCIe ordering deviation pending ratification (`docs/discussions/backend-lowering/README.md:75`, `docs/discussions/backend-lowering/README.md:86`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:58`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:70`).

The shared invariant says the bus preamble is ordered `enable_device -> claim_regions -> set_bus_master -> get_resource_handle -> map_region`, and the reference code emits `enable_device` before `get_resource_handle` (`docs/discussions/backend-lowering/README.md:75`, `docs/discussions/backend-lowering/README.md:86`; `crates/regseq-backends/src/generic_c/body_emit.rs:5219`, `crates/regseq-backends/src/generic_c/body_emit.rs:5285`). Linux preserves that sequence inside `.probe`, with only `register_driver` hoisted to module init (`docs/discussions/linux-backend/linux-integration-probe-path.md:152`, `docs/discussions/linux-backend/linux-integration-probe-path.md:161`).

Zephyr's PCIe path explicitly inverts part of that order by probing the BAR before enabling memory decode, records that as `probe -> enable -> map`, and marks it pending ratification as BRM-O2/A-3 (`docs/discussions/zephyr-backend/zephyr-model-analysis.md:167`, `docs/discussions/zephyr-backend/zephyr-model-analysis.md:169`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:58`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:70`; `docs/discussions/zephyr-backend/zephyr-scaffold-and-dispatch.md:146`, `docs/discussions/zephyr-backend/zephyr-scaffold-and-dispatch.md:156`). The same Zephyr integration doc later says canonical order is preserved across binding times, but it also names the PCIe probe-before-enable case as the single recorded deviation pending ratification (`docs/discussions/zephyr-backend/zephyr-integration-probe-path.md:102`, `docs/discussions/zephyr-backend/zephyr-integration-probe-path.md:114`; `docs/discussions/zephyr-backend/zephyr-integration-probe-path.md:259`, `docs/discussions/zephyr-backend/zephyr-integration-probe-path.md:271`).

Resolution required: either ratify Zephyr PCIe as a formal per-OS shell permutation and state that the shared invariant allows this exact reference-driven exception, or require generated Zephyr PCIe code to preserve canonical `enable -> handle -> map` order (`docs/discussions/backend-lowering/model-analysis-strategy.md:227`, `docs/discussions/backend-lowering/model-analysis-strategy.md:241`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:58`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:70`).

### F2. The foundation still says Zephyr-over-PCI is deferred, while the Zephyr spec resolves it

Classification: stale shared-foundation inconsistency, not an OS-semantic disagreement, because the foundation still defers Zephyr-over-PCI while the Zephyr sweep and README resolve it affirmatively (`docs/discussions/backend-lowering/model-analysis-strategy.md:139`, `docs/discussions/backend-lowering/model-analysis-strategy.md:162`; `docs/discussions/zephyr-backend/zephyr-model-analysis.md:21`, `docs/discussions/zephyr-backend/zephyr-model-analysis.md:33`; `docs/discussions/zephyr-backend/README.md:164`, `docs/discussions/zephyr-backend/README.md:177`).

The shared strategy doc pins Zephyr to devicetree/platform-style devices, marks `read_config`/`write_config` as not-applicable for Zephyr, and says Zephyr-over-PCI is deferred unless a trivial mapping appears (`docs/discussions/backend-lowering/model-analysis-strategy.md:139`, `docs/discussions/backend-lowering/model-analysis-strategy.md:162`; `docs/discussions/backend-lowering/model-analysis-strategy.md:168`, `docs/discussions/backend-lowering/model-analysis-strategy.md:190`). The Zephyr spec now says the PCI question is answered affirmatively, because the vendored e1000 port demonstrates a PCIe host layer and bring-up idiom, and the Zephyr README repeats that `BusType::Pci` is lowerable on Zephyr with version-pinning caveats (`docs/discussions/zephyr-backend/zephyr-model-analysis.md:21`, `docs/discussions/zephyr-backend/zephyr-model-analysis.md:33`; `docs/discussions/zephyr-backend/README.md:164`, `docs/discussions/zephyr-backend/README.md:177`).

Resolution required: update the foundation strategy's Zephyr target pin to say the original PCI deferral is superseded by the Zephyr sweep, while keeping the version-sensitive PCIe details in Zephyr open questions (`docs/discussions/zephyr-backend/zephyr-model-analysis.md:340`, `docs/discussions/zephyr-backend/zephyr-model-analysis.md:365`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:331`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:335`).

### F3. `_STATUS.md` contradicts the current tree

Classification: stale status inconsistency, not an OS-specific divergence, because `_STATUS.md` says Zephyr is absent while the Zephyr directory declares a complete five-construct spec (`docs/discussions/backend-lowering/_STATUS.md:17`, `docs/discussions/backend-lowering/_STATUS.md:24`; `docs/discussions/zephyr-backend/README.md:1`, `docs/discussions/zephyr-backend/README.md:22`).

`_STATUS.md` says the deliverable is incomplete because the Zephyr track was not attempted, that `docs/discussions/zephyr-backend/` does not exist, and that Zephyr-over-PCI remains open from the task brief (`docs/discussions/backend-lowering/_STATUS.md:12`, `docs/discussions/backend-lowering/_STATUS.md:24`). The current Zephyr README says `docs/discussions/zephyr-backend/` is a complete Zephyr backend lowering spec for the five constructs, and the Zephyr model analysis states every primitive row was swept with no `?` dispositions left (`docs/discussions/zephyr-backend/README.md:1`, `docs/discussions/zephyr-backend/README.md:22`; `docs/discussions/zephyr-backend/zephyr-model-analysis.md:1`, `docs/discussions/zephyr-backend/zephyr-model-analysis.md:11`).

`_STATUS.md` also says the Linux track rated all five constructs fully lowerable, while the Linux open-question ledger now distinguishes "core subset lowerable" from "complete construct lowerable" and says no construct earns the latter (`docs/discussions/backend-lowering/_STATUS.md:94`, `docs/discussions/backend-lowering/_STATUS.md:103`; `docs/discussions/linux-backend/linux-open-questions.md:254`, `docs/discussions/linux-backend/linux-open-questions.md:270`). This should be updated or clearly marked as superseded before readers use `_STATUS.md` as a hand-off document (`docs/discussions/backend-lowering/_STATUS.md:1`, `docs/discussions/backend-lowering/_STATUS.md:8`).

### F4. Completeness wording is not comparable across OS docs

Classification: terminology inconsistency; the underlying residual gaps are mostly OS-specific, because Linux and Zephyr both list residual gaps while using different completeness terms (`docs/discussions/linux-backend/linux-open-questions.md:258`, `docs/discussions/linux-backend/linux-open-questions.md:270`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:380`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:388`).

Linux's ledger intentionally says every construct is a lowerable core subset or mechanism, but not a complete construct, because residual gaps remain (`docs/discussions/linux-backend/linux-open-questions.md:258`, `docs/discussions/linux-backend/linux-open-questions.md:270`). Zephyr's ledger uses "fully specified" for register-access, diagnostics-logging, and RegseqError, while still listing residual gaps and exercised-shape caveats for the same ledger (`docs/discussions/zephyr-backend/zephyr-open-questions.md:380`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:388`).

The shared method defines completion as a row-by-row disposition/citation/open-question/drop/needs-new-surface check, not as "the construct has no residual gaps" (`docs/discussions/backend-lowering/model-analysis-strategy.md:227`, `docs/discussions/backend-lowering/model-analysis-strategy.md:241`). Resolution required: add a shared status vocabulary such as "sweep complete", "core subset lowerable", "specified for exercised shapes", and "complete construct lowerable", then make the Linux and Zephyr ledgers use those terms consistently (`docs/discussions/linux-backend/linux-open-questions.md:258`, `docs/discussions/linux-backend/linux-open-questions.md:270`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:380`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:388`).

### F5. Zephyr still has a citation-shorthand cleanup gap

Classification: documentation-hygiene inconsistency against the shared citation rule, not an OS-semantic divergence, because the foundation requires repo-rooted `path:line` or pinned OS-doc citations and the Zephyr ledger keeps a residual shorthand-expansion task (`docs/discussions/backend-lowering/README.md:97`, `docs/discussions/backend-lowering/README.md:106`; `docs/discussions/zephyr-backend/zephyr-open-questions.md:187`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:194`).

The foundation requires every normative claim to cite a repo `path:line` or pinned OS-doc URL, and the Zephyr README permits shorthand basenames via a legend (`docs/discussions/backend-lowering/README.md:97`, `docs/discussions/backend-lowering/README.md:106`; `docs/discussions/zephyr-backend/README.md:140`, `docs/discussions/zephyr-backend/README.md:149`). Zephyr's own open-question ledger says many normative claims still cite bare basenames or sibling sections rather than repo-rooted `path:line`, and recommends a dedicated mechanical sweep (`docs/discussions/zephyr-backend/zephyr-open-questions.md:187`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:194`).

Resolution required: expand Zephyr shorthand citations to repo-rooted `path:line` references before treating Zephyr's citation discipline as equivalent to the foundation rule (`docs/discussions/zephyr-backend/zephyr-open-questions.md:396`, `docs/discussions/zephyr-backend/zephyr-open-questions.md:403`).

## Input-contract answer

The two OS specs agree on the shared input contract: a backend reads `RegseqModel` plus `BackendContext`, reuses the type/layout/name/body machinery, recognizes the same domain attrs and lifecycle side tables, and replaces only the OS-shell materialization targets (`docs/discussions/backend-lowering/regseqmodel-input-contract.md:26`, `docs/discussions/backend-lowering/regseqmodel-input-contract.md:69`; `docs/discussions/backend-lowering/agnostic-core-vs-os-shell.md:178`, `docs/discussions/backend-lowering/agnostic-core-vs-os-shell.md:243`; `docs/discussions/backend-lowering/agnostic-core-vs-os-shell.md:265`, `docs/discussions/backend-lowering/agnostic-core-vs-os-shell.md:291`).

The only input-contract drift is editorial: shared foundation/status docs still describe the old Zephyr scope and old deliverable state, while the Zephyr track now provides a PCIe-aware sweep and a full current ledger (`docs/discussions/backend-lowering/model-analysis-strategy.md:139`, `docs/discussions/backend-lowering/model-analysis-strategy.md:162`; `docs/discussions/backend-lowering/_STATUS.md:17`, `docs/discussions/backend-lowering/_STATUS.md:24`; `docs/discussions/zephyr-backend/zephyr-model-analysis.md:21`, `docs/discussions/zephyr-backend/zephyr-model-analysis.md:33`; `docs/discussions/zephyr-backend/zephyr-model-analysis.md:340`, `docs/discussions/zephyr-backend/zephyr-model-analysis.md:365`).
