# Driver Lifecycle Taxonomy Review

**Construct:** `driver-lifecycle`  
**Target OS set:** Linux, Zephyr, Windows, FreeBSD, macOS  
**Review framing:** author-semantic surface only

## Executive summary

The `Driver Lifecycle` construct captures the driver author's **device-binding contract**: what devices the driver supports, what device class it implements, and what custom code must run when a matched device instance is initialized or torn down.

Under the rule that the taxonomy should capture only what **cannot be inferred or generated by the compiler**, the current construct has the right conceptual core but should be refined. The compiler can generate OS registration glue, callback tables, context association, private-data plumbing, and resource preamble/postamble sequencing. The author-facing surface should therefore be limited to:

- driver identity,
- typed match intent,
- device class,
- optional active probe / validation,
- optional custom initialization,
- optional custom teardown.

**Current quality score:** 7.0 / 10  
**Expected score after refinement:** approximately 8.5 / 10

The main weaknesses are:

1. macOS is absent from the current lowering model.
2. `compatible` is too flat for a five-OS matching model.
3. active probe / match validation is missing.
4. teardown reason and hardware-access guarantees are under-specified.
5. the taxonomy over-prominently lists compiler-generated operations as if they were part of the construct's semantic operation surface.
6. requiring a `Lifecycle` trait implementation even when the author has no custom lifecycle logic is too strict.

---

## 1. What aspect of device driver specification does this construct capture?

`Driver Lifecycle` captures the **semantic contract for binding a Regseq driver to a concrete device instance**.

More precisely, it captures the author-provided information needed to answer:

> What devices does this driver claim to support, what device class does it implement, and what custom author code must run when a matched device instance becomes available or is being torn down?

The current taxonomy describes this as a driver author writing:

```rust
#[rseq::driver(name = "...", compatible = [...])]
#[rseq::device_class(...)]
```

and implementing `Lifecycle::init` / `Lifecycle::deinit`. The compiler then emits bus-level registration, device creation, and private-data association.

At the semantic level, the construct should own only those lifecycle facts that the compiler cannot infer safely.

| Lifecycle concern | Should `Driver Lifecycle` capture it? | Reason |
|---|---:|---|
| Driver identity | Yes | The compiler cannot infer the stable logical name the author wants used for registration, diagnostics, generated symbols, and target metadata. |
| Device match intent | Yes | The author must say which hardware descriptions this driver supports. |
| Device class | Yes | The author must state whether the driver is serial, network, generic, etc., because this gates class-specific contracts. |
| Custom per-device initialization | Yes, but only when needed | The compiler can generate empty/default init, but cannot infer driver-specific setup logic. |
| Custom per-device teardown | Yes, but only when needed | The compiler can release declared Regseq resources, but cannot infer custom state unwinding. |
| Optional active match validation | Yes | The compiler cannot infer hardware-revision checks, capability checks, or probe ranking logic. |
| OS registration boilerplate | No | The compiler should generate Linux driver structs, Zephyr device definitions, Windows WDF callbacks, FreeBSD Newbus tables, and macOS I/O Kit / DriverKit metadata. |
| Private-data association | No | The compiler can generate `dev_set_drvdata`, WDF context setup, FreeBSD softc association, Zephyr static device data, and macOS service state binding. |
| Suspend/resume | No | This belongs to `Device Power State Management`, not `Driver Lifecycle`. |
| Resource acquisition | No, except ordering coordination | MMIO, DMA, IRQ, clocks, resets, pinctrl, and firmware properties belong to their own constructs. |

This is a legitimate OS-agnostic construct because all target OSes have the same logical lifecycle problem, even though their mechanisms differ:

- Linux binds a driver to a device through bus-specific matching and calls the driver's probe path for binding-specific setup.
- Zephyr creates device objects through its device model and initializes them through generated device definitions or init handlers.
- Windows KMDF separates device-add, hardware-preparation, power, and release callbacks.
- FreeBSD Newbus uses probe, attach, and detach methods.
- macOS I/O Kit uses matching, probing, start/stop, and object lifecycle methods.

The Regseq construct should abstract over those mechanisms while preserving the author's actual semantic intent.

## 2. What semantic properties and operations are captured?

## 2.1 Current captured properties

The current taxonomy captures three author-facing properties.

| Current property | Current surface | Semantic meaning | Assessment |
|---|---|---|---|
| `driver_lifecycle.driver_name` | `#[rseq::driver(name = "...")]` | Stable logical driver identity. | Good and necessary. |
| `driver_lifecycle.compatible` | `#[rseq::driver(compatible = [...])]` | Match-id list used for device binding. | Directionally correct, but too flat for five-OS coverage. |
| `driver_lifecycle.device_class` | `#[rseq::device_class(...)]` | Declares the class contract, such as Serial or Network. | Good, but should allow `generic` / `none` for drivers with no class-specific public interface. |

The strongest property is `device_class`. It is not merely metadata; it determines which device-class taxonomy the driver must also satisfy. For example, a serial driver should implement serial-class operations, and a network driver should implement network-class operations.

The weakest property is `compatible`. A simple string list is adequate for a device-tree-first model, but incomplete for a five-OS model. PCI IDs, USB IDs, ACPI HIDs/CIDs, device-tree compatibles, Windows hardware IDs, and macOS I/O Kit personality dictionaries are structurally different kinds of match evidence. Treating them all as untyped strings blurs important semantics.

## 2.2 Current captured operations

The current taxonomy captures two author-facing trait methods and three compiler-managed operations.

| Current operation | Current role | Author-facing? | Assessment |
|---|---|---:|---|
| `driver_lifecycle.init` | Driver-implemented init callback after compiler preamble | Yes | Valid, but should not be mandatory when empty. |
| `driver_lifecycle.deinit` | Driver-implemented teardown callback before compiler postamble | Yes | Valid, but the hardware-access guarantee needs refinement. |
| `driver_lifecycle.register_driver` | Compiler-managed bus-level registration | No | Should be internal lowering obligation, not author surface. |
| `driver_lifecycle.create_device` | Compiler-managed instance construction | No | Should be internal lowering obligation. |
| `driver_lifecycle.associate_private_data` | Compiler-managed private-data association | No | Should be internal lowering obligation. |

The current taxonomy already marks `register_driver`, `create_device`, and `associate_private_data` as compiler-managed. That is good. The refinement is presentational and conceptual: these should not be treated as lifecycle **operations captured from the driver author's specification**. They are backend obligations derived from the driver's descriptor and declared resources.

## 2.3 Core semantic invariants currently captured

| Invariant | Current taxonomy treatment | Assessment |
|---|---|---|
| Init runs after compiler preamble | `init` runs after firmware properties, MMIO, clocks, resets, pinctrl, IRQ, timers, and DMA resources are populated. | Good. |
| Deinit runs before compiler postamble | `deinit` runs before dependent resources are released. | Good in intent, but target-specific hardware-access semantics need refinement. |
| Lifecycle is separate from power management | `suspend` / `resume` are explicitly excluded and routed to Power Management. | Correct. |
| Object-model state is not author surface | Track-B object-model state is kept as compiler-derived rationale only. | Correct under the author-surface rule. |
| Device-class trait checks are tied to lifecycle metadata | `device_class` gates class-specific trait implementations. | Good. |

## 3. Semantic gaps found and evidence

## Gap 1 — macOS is absent from the current lowering model

The uploaded taxonomy provides lowering rows for Linux, Zephyr, FreeBSD, and Windows, but not macOS.

This is a real completeness gap because macOS has a distinct lifecycle model. I/O Kit's IOService lifecycle includes object creation/destruction, matching/probing, provider attachment, and start/stop phases. I/O Kit matching also supports passive matching through personality dictionaries and active probing with probe scores.

**Evidence:**

- Apple I/O Kit Fundamentals, architecture overview: https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/ArchitectOverview/ArchitectOverview.html
- Apple I/O Kit matching documentation: https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/Matching/Matching.html

**Impact:** The author surface may remain small, but the taxonomy needs explicit macOS lowering for at least static match metadata, optional active probe, init/start, and deinit/stop.

---

## Gap 2 — compiler-generated operations are over-prominent in the construct

The current taxonomy lists `register_driver`, `create_device`, and `associate_private_data` as operations. It marks them as compiler-managed, but they appear alongside author-facing lifecycle callbacks.

Under the author-surface rule, these should be moved to a separate section such as **Compiler-derived lowering obligations**. The driver author should not specify these operations. The author only provides semantic facts from which the compiler generates them.

**Evidence:**

The current uploaded taxonomy explicitly marks these operations as compiler-managed. This supports reclassifying them as lowering obligations rather than author-specified operations.

**Impact:** This is not a functional gap, but it is a taxonomy-quality issue. It risks making the construct look more OS-mechanism-oriented than it should be.

---

## Gap 3 — `compatible` is too flat for five-OS matching

The current `compatible` property is a required list of match-id strings. That is reasonable for device-tree-like matching, but incomplete as a five-OS semantic model.

| Target | Match mechanism evidence | Why flat `compatible: [string]` is insufficient |
|---|---|---|
| Linux | Linux driver registration is bus-specific, and driver structures carry bus-specific IDs and callbacks. | PCI IDs, OF compatibles, ACPI IDs, USB IDs, and I2C IDs have different fields. |
| Zephyr | Zephyr device objects are commonly defined from devicetree nodes through device-definition macros. | Devicetree compatible strings work, but init level, device API metadata, and generated device data also matter. |
| Windows | KMDF `EvtDriverDeviceAdd` is called after a bus driver detects a matching device. Supported IDs are represented through installation / PnP metadata. | Windows hardware IDs and compatible IDs are not the same as device-tree-compatible strings. |
| FreeBSD | Newbus uses device methods including `probe`, `attach`, and `detach`, with bus-specific matching behavior. | Probe/attach behavior may depend on bus-specific IDs and probe return priority. |
| macOS | I/O Kit uses class matching, passive matching against personality dictionaries, and active probing. | I/O Kit personality dictionaries cannot be represented faithfully as an untyped string list. |

**Evidence:**

- Linux driver model documentation: https://docs.kernel.org/driver-api/driver-model/driver.html
- Zephyr device model documentation: https://docs.zephyrproject.org/latest/doxygen/html/group__device__model.html
- Windows KMDF `EvtDriverDeviceAdd`: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdriver/nc-wdfdriver-evt_wdf_driver_device_add
- FreeBSD Newbus architecture handbook: https://docs.freebsd.org/en/books/arch-handbook/newbus/
- Apple I/O Kit matching documentation: https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/Matching/Matching.html

**Impact:** The taxonomy should replace `compatible` with a typed `match_set`, while allowing `compatible` as shorthand for devicetree-compatible entries.

## Gap 4 — optional active probe / validation is missing

The current taxonomy has only `init` and `deinit`; it does not expose a semantic operation for active match validation or match ranking.

This matters because several OSes expose a pre-bind or early-bind phase where the driver may need to inspect the device before committing:

- Linux `probe()` is where the driver verifies that the device is present and supported, allocates state, and initializes hardware.
- FreeBSD Newbus explicitly separates `probe`, `attach`, and `detach`.
- macOS I/O Kit active matching can invoke `probe`, allow probe-score adjustment, and requires probe not to leave hardware mutated for the next candidate.

This does **not** mean every Regseq driver needs a `probe` method. Most drivers can rely on static matching plus compiler-generated resource validation. But when a driver author needs to express “I must inspect hardware revision or capability before accepting this device,” the current taxonomy has no clean author surface for that intent.

**Evidence:**

- Linux driver model documentation: https://docs.kernel.org/driver-api/driver-model/driver.html
- FreeBSD Newbus architecture handbook: https://docs.freebsd.org/en/books/arch-handbook/newbus/
- Apple I/O Kit matching documentation: https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/Matching/Matching.html

**Impact:** Add an optional `Lifecycle::probe` or `Lifecycle::match_device` hook, with strict side-effect rules. It should be absent by default.

---

## Gap 5 — `init` and `deinit` are too coarse as currently worded

The current `init` operation is described as running after the compiler preamble has populated resources. The current `deinit` operation is described as running before resource release while the driver may still touch declared resources.

That wording is too coarse for Windows and macOS.

Windows separates several phases: `EvtDriverDeviceAdd` creates and configures the framework device, `EvtDevicePrepareHardware` receives raw and translated hardware resources after PnP resource assignment, and later power callbacks control D0 entry/exit. `EvtDeviceReleaseHardware` is called when hardware resources are being released, including resource rebalancing, orderly removal, and surprise removal.

macOS also has richer lifecycle pairs such as `init/free`, `attach/detach`, `probe`, and `start/stop`.

**Evidence:**

- Windows KMDF `EvtDriverDeviceAdd`: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdriver/nc-wdfdriver-evt_wdf_driver_device_add
- Windows KMDF `EvtDevicePrepareHardware`: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdevice/nc-wdfdevice-evt_wdf_device_prepare_hardware
- Windows KMDF `EvtDeviceReleaseHardware`: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdevice/nc-wdfdevice-evt_wdf_device_release_hardware
- Apple I/O Kit architecture overview: https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/ArchitectOverview/ArchitectOverview.html

**Impact:** Regseq should define lifecycle phases semantically rather than mapping `init` naively to whichever OS callback has a similar name. In particular, author-facing `init` should mean:

> Resources declared in Regseq are available, the device has been accepted for this driver, and custom author initialization may now run.

It should not mean:

> Whatever the target OS happens to call `init`.

---

## Gap 6 — teardown reason and hardware-access guarantee are missing

The current `deinit` description says the driver may still touch declared MMIO, clocks, reset lines, and IRQs before compiler postamble release.

That guarantee is not uniformly true across targets and removal scenarios.

For example, Windows `EvtDeviceReleaseHardware` may run for resource rebalancing, orderly removal, or surprise removal. Depending on the path, I/O may already be stopped, interrupts may be disabled, and hardware may not be reliably accessible. macOS also distinguishes quiescence-style `stop` from final object cleanup.

**Evidence:**

- Windows KMDF `EvtDeviceReleaseHardware`: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdevice/nc-wdfdevice-evt_wdf_device_release_hardware
- Apple I/O Kit architecture overview: https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/IOKitFundamentals/ArchitectOverview/ArchitectOverview.html

**Impact:** `deinit` should receive a semantic `DeinitReason`, and the taxonomy should define whether hardware access is guaranteed, prohibited, or target/removal-path dependent at that point.

---

## Gap 7 — requiring every driver to implement `Lifecycle` violates the author-surface rule

The current diagnostics say to reject driver types missing a `Lifecycle` implementation.

Under the author-surface rule, this is too strict. If a driver has no custom lifecycle logic, the compiler can generate no-op init/deinit and still perform all declared Regseq resource setup and teardown.

**Impact:** `Lifecycle` implementation should be optional. The required author surface should be the driver descriptor and device-class declaration, not necessarily lifecycle callback bodies.

---

## Gap 8 — partial initialization and failure rollback need a compiler-visible state machine

The current taxonomy says `init` returns `RegseqError` on failure and the framework propagates the failure; it also says the deinit path runs to release acquired resources. That is a good start, but it does not fully specify what happens if:

- the compiler preamble succeeds partially,
- author `init` fails midway,
- a dependent resource constructor fails,
- a class registration occurs before a later init step fails,
- a target OS does not call the same teardown callback after failed initialization.

Windows explicitly states that if `EvtDevicePrepareHardware` fails, the framework calls `EvtDeviceReleaseHardware`. Linux probe failure normally requires the probe path to unwind what it acquired before returning failure.

**Evidence:**

- Windows KMDF `EvtDevicePrepareHardware`: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdevice/nc-wdfdevice-evt_wdf_device_prepare_hardware
- Linux driver model documentation: https://docs.kernel.org/driver-api/driver-model/driver.html

**Impact:** This should be a compiler state-machine invariant, not an author operation. The author only needs a clear contract:

> If `init` fails, Regseq will unwind all compiler-managed resources. Custom side effects must either be represented as Regseq resources or cleaned up by the author before returning the error.

## 4. Recommended refined taxonomy

## 4.1 Recommended construct meaning

**Refined definition:**

`Driver Lifecycle` defines the author-provided semantic descriptor and optional lifecycle callbacks needed to bind a Regseq driver to a device instance. The compiler uses this information to generate target-specific registration, matching, object creation, context association, callback glue, resource-preamble/postamble sequencing, and failure rollback.

This definition keeps the author surface small and moves generated OS mechanics out of the construct's public operation set.

---

## 4.2 Refined author-facing properties

| Refined property | Required? | Type | Meaning | Notes |
|---|---:|---|---|---|
| `driver.name` | Yes | string | Stable logical driver identity. | Replaces / preserves `driver_lifecycle.driver_name`. |
| `driver.match_set` | Yes | list of typed match entries | The hardware descriptions this driver supports. | Refines `compatible`. |
| `driver.device_class` | Yes | enum/tag | Device-class contract: `serial`, `network`, `generic`, etc. | `generic` should be valid when no class taxonomy applies. |
| `driver.lifecycle.probe_policy` | Optional | enum | Whether author supplies active validation/ranking. | Default: `static_match_only`. |
| `driver.lifecycle.teardown_contract` | Optional | enum | Whether author deinit requires hardware access. | Default: `software_only_or_best_effort`. |
| `driver.lifecycle.publish_policy` | Optional | enum | Whether device-class publication occurs before or after author init. | Usually compiler-inferred from class taxonomy. |

### Recommended `match_set` shape

Instead of this flat form:

```rust
#[rseq::driver(compatible = ["vendor,device"])]
```

use a typed match schema, while allowing devicetree shorthand:

```rust
#[rseq::driver(
    name = "e1000",
    match = [
        pci(vendor = 0x8086, device = 0x100E),
        acpi(hid = "INTCxxxx"),
        devicetree(compatible = "vendor,e1000"),
        windows_hardware_id("PCI\\VEN_8086&DEV_100E"),
        macos_personality(provider = "IOPCIDevice", class = "RegseqE1000")
    ]
)]
```

A lighter v1 version could be:

```rust
#[rseq::driver(
    name = "ns16550",
    match = [
        devicetree("ns16550"),
        acpi("PNP0501")
    ]
)]
```

The key refinement is that `compatible` should become a **typed match set**, not a generic string list.

## 4.3 Refined author-facing operations

## Operation 1: Optional active probe

```rust
trait Lifecycle {
    fn probe(ctx: ProbeContext) -> ProbeDecision {
        ProbeDecision::Accept
    }
}
```

### Semantic meaning

`probe` is an optional author-supplied validation/ranking hook used only when static match metadata is insufficient.

### Suggested return type

```rust
enum ProbeDecision {
    Accept,
    Reject,
    AcceptWithScore(i32),
}
```

### Rules

| Rule | Meaning |
|---|---|
| Default is `Accept` | Most drivers do not need to implement this. |
| Must be side-effect neutral | If it touches hardware, it must leave hardware as it found it. This matches macOS probing expectations. |
| Ranking is capability-gated | macOS and FreeBSD-style probe ranking can use scores; Windows and Zephyr generally lower this to accept/reject validation, not competitive ranking. |
| May read immutable identity registers | Useful for revision checks, capability checks, and variant discrimination. |
| Must not allocate long-lived resources | Long-lived setup belongs in `init`. |

### Lowering sketch

| Target | Lowering |
|---|---|
| Linux | Early portion of `probe()` before full resource acquisition, or after minimal compiler preamble when needed. |
| Zephyr | Compile-time static match by default; optional runtime validation inside init, failing init if rejected. |
| Windows | Post-match validation in `EvtDriverDeviceAdd` or `EvtDevicePrepareHardware`; no general probe-score competition. |
| FreeBSD | `DEVICE_PROBE`, with score mapping where applicable. |
| macOS | `IOService::probe` / DriverKit equivalent, preserving score semantics where supported. |

---

## Operation 2: Optional init

```rust
trait Lifecycle {
    fn init(&mut self) -> Result<(), RegseqError> {
        Ok(())
    }
}
```

### Semantic meaning

`init` runs once per accepted device instance **after** the compiler has completed all declared Regseq resource preamble work that the driver is allowed to rely on.

### Refined precondition

Before `init`, the compiler has already performed all declared and inferable setup:

- firmware property population,
- driver instance construction,
- private context association,
- bus-handle capture,
- MMIO mapping,
- declared clock/reset/pinctrl setup,
- declared interrupt registration if required before author init,
- declared DMA setup if required before author init.

### Refined postcondition

After `init` succeeds:

- the driver's custom state is initialized,
- the device may be published through its device-class interface,
- class-specific registration may occur either inside `init` or in compiler-generated class glue, depending on the class taxonomy.

### Important refinement

`init` should be **optional**. A driver that only declares resources and implements class operations should not need to write an empty `Lifecycle::init`.

---

## Operation 3: Optional deinit / stop

```rust
trait Lifecycle {
    fn deinit(&mut self, reason: DeinitReason) {
        // default no-op
    }
}
```

### Suggested `DeinitReason`

```rust
enum DeinitReason {
    OrderlyRemove,
    DriverUnload,
    ResourceRebalance,
    SurpriseRemove,
    InitFailureRollback,
    Rebind,
    Shutdown,
}
```

### Semantic meaning

`deinit` runs when the device instance is leaving the Regseq-bound state. It is for author-defined teardown that the compiler cannot infer.

### Refined hardware-access rule

The current taxonomy says the driver may still touch MMIO, clocks, reset lines, and IRQs during `deinit`. That should be replaced with a more precise rule:

```rust
enum TeardownAccess {
    HardwareAccessible,
    HardwareMaybeInaccessible,
    SoftwareOnly,
}
```

Default should be `SoftwareOnly` or `HardwareMaybeInaccessible`, not `HardwareAccessible`.

### Lowering sketch

| Target | Lowering |
|---|---|
| Linux | `remove()` path, plus compiler-generated pre/post teardown ordering. |
| Zephyr | `DEVICE_DT_DEINIT_DEFINE` / deinit hook where available; otherwise static/no-op teardown where runtime unload is unsupported. |
| Windows | Split lowering: hardware quiescence should occur before or during D0 exit / stop phases; software release maps to `EvtDeviceReleaseHardware` or object cleanup. |
| FreeBSD | `DEVICE_DETACH`, with busy/removal semantics handled by target lowering. |
| macOS | `stop` for quiescence; `free` / object cleanup for final release, depending on whether the author callback needs hardware access. |

---

## Optional Operation 4: Query remove / can detach

This should be **future or capability-gated**, not v1 required.

```rust
trait Lifecycle {
    fn can_remove(&self, reason: RemoveQueryReason) -> RemoveDecision {
        RemoveDecision::Allow
    }
}
```

### Why not required in v1?

Some OSes have removal-veto or query-stop concepts, while others do not expose a comparable portable mechanism. Windows has QueryRemove / QueryStop style PnP callbacks in the broader WDF callback family, and FreeBSD detach may have busy semantics, but Linux and Zephyr do not map cleanly to a general “veto removal” contract.

This can be included as a semantic-union extension, but it should be target-capability-gated.

---

## 4.4 Refined compiler-managed lowering obligations

These should remain in the taxonomy, but not as author-facing operations.

| Compiler-managed obligation | Current operation name | Refined classification |
|---|---|---|
| Generate OS driver registration | `driver_lifecycle.register_driver` | Internal lowering obligation |
| Construct per-device instance | `driver_lifecycle.create_device` | Internal lowering obligation |
| Associate OS handle with Regseq state | `driver_lifecycle.associate_private_data` | Internal lowering obligation |
| Generate match tables / metadata | currently folded into `compatible` lowering | Internal lowering obligation derived from `match_set` |
| Generate callback trampolines | implicit | Internal lowering obligation |
| Run resource preamble/postamble | described in `init` / `deinit` | Cross-construct compiler state machine |
| Unwind partial init failures | partially described | Compiler state-machine obligation |
| Enforce device-class trait requirements | current diagnostic | Compiler validation obligation |

## 4.5 Recommended refined YAML-style taxonomy

```yaml
construct: driver-lifecycle
purpose: >
  Capture author-provided device-binding identity, match intent, device-class
  contract, and optional custom lifecycle behavior. OS registration,
  object creation, context association, callback glue, and resource ordering
  are compiler-generated.

author_surface:
  properties:
    - stable_id: driver.name
      type: string
      required: true
      meaning: Stable logical driver identity.

    - stable_id: driver.match_set
      type: list<MatchEntry>
      required: true
      meaning: Typed set of hardware descriptions this driver supports.
      allowed_entries:
        - devicetree_compatible
        - acpi_hid_cid
        - pci_id
        - usb_id
        - i2c_id
        - spi_id
        - windows_hardware_id
        - macos_personality
      note: >
        `compatible = [...]` may remain shorthand for devicetree-compatible
        entries, but should not be the universal representation.

    - stable_id: driver.device_class
      type: enum | tag
      required: true
      examples: [serial, network, generic]
      meaning: Device-class contract implemented by the driver.

    - stable_id: lifecycle.probe_policy
      type: enum
      required: false
      default: static_match_only
      values:
        - static_match_only
        - validate_after_match
        - rank_candidates_when_supported

    - stable_id: lifecycle.teardown_contract
      type: enum
      required: false
      default: software_only_or_best_effort
      values:
        - hardware_access_required
        - hardware_maybe_inaccessible
        - software_only

  operations:
    - stable_id: lifecycle.probe
      required: false
      signature: "fn probe(ctx: ProbeContext) -> ProbeDecision"
      default: "Accept"
      meaning: Optional author-supplied active match validation or ranking.
      constraints:
        - side_effect_neutral
        - no_long_lived_resource_allocation
        - ranking_is_target_capability_gated

    - stable_id: lifecycle.init
      required: false
      signature: "fn init(&mut self) -> Result<(), RegseqError>"
      default: "Ok(())"
      meaning: Custom author initialization after compiler resource preamble.

    - stable_id: lifecycle.deinit
      required: false
      signature: "fn deinit(&mut self, reason: DeinitReason)"
      default: "no-op"
      meaning: Custom author teardown before or during compiler-managed release.
      constraints:
        - hardware_access_allowed_only_if_teardown_contract_permits

compiler_managed:
  obligations:
    - generate_target_driver_registration
    - generate_match_tables_or_personalities
    - create_per_device_instance
    - associate_private_context
    - generate_callback_trampolines
    - run_declared_resource_preamble_before_init
    - run_declared_resource_postamble_after_deinit
    - implement_partial_init_rollback
    - enforce_device_class_trait_requirements

explicitly_out_of_scope:
  - suspend_resume_power_transitions
  - runtime_power_management
  - bus_resource_acquisition_details
  - interrupt_registration_details
  - dma_setup_details
  - client_open_close_session_lifecycle
  - child_device_enumeration
```

## 4.6 Recommended diagnostics

| Diagnostic | Severity | Rationale |
|---|---|---|
| Missing `driver.name` | Error | Cannot generate stable registration/logging identity. |
| Missing `driver.match_set` | Error | Cannot bind driver to hardware. |
| Untyped legacy `compatible` used for non-devicetree target | Warning or error | A string list is ambiguous for PCI/ACPI/Windows/macOS. |
| Missing `device_class` | Error unless default `generic` is allowed | Class contract must be known. |
| `Lifecycle` trait absent | No error | Compiler generates no-op lifecycle callbacks. |
| `init` touches unavailable resource | Error | Resource dependency must be declared or reordered. |
| `probe` has non-neutral side effects | Error | Active probe must not commit hardware state. |
| `probe` returns score on target without ranking support | Warning or target-gated error | Windows/Zephyr cannot generally honor dynamic probe-score semantics. |
| `deinit` requires hardware access on a target/removal path where hardware may be gone | Error or requires fallback path | Prevents surprise-removal unsoundness. |
| Custom init allocates non-Regseq resource without teardown path | Warning | Helps enforce rollback safety. |
| Device-class mismatch | Error | Example: `device_class = serial` without Serial class implementation. |

---

## Bottom-line recommendation

The current `Driver Lifecycle` taxonomy has the right conceptual core, but it should be refined in three main ways.

First, **shrink the author surface**. Keep only `driver.name`, typed `match_set`, `device_class`, and optional lifecycle callbacks. Move `register_driver`, `create_device`, and `associate_private_data` to compiler-managed lowering obligations.

Second, **replace flat `compatible` with typed matching**. A five-OS taxonomy needs typed match entries for devicetree, ACPI, PCI, USB, Windows hardware IDs, and macOS personalities.

Third, **add optional active probe and richer teardown semantics**. `probe` is only needed when static matching is insufficient. `deinit` should receive a reason and should not assume hardware is always accessible, especially for Windows surprise removal and macOS stop/free distinctions.

With these refinements, the construct would move from roughly **7.0 / 10** to **8.5 / 10** for Linux, Zephyr, Windows, FreeBSD, and macOS.
