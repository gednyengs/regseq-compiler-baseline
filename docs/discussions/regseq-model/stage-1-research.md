# Stage 1: Prior-Art Research and Locked Sub-Decisions

Research synthesis that informs the Stage 1 ("vocabulary") spec. Captures
the prior-art reading across four clusters, the convergent patterns that
fall out of that reading, and the four stage-1 sub-decisions (F1-F4) that
required explicit calls.

This is *not* the spec. The spec lives at `stage-1-vocabulary.md` (to be
authored after Codex review of this document). This is the evidence base
that the spec rests on.

## Scope

Stage 1 specifies the foundational table-and-id scaffolding that every
later stage of RegseqModel rides on:

1. ID types (item, body, ty, const, block, local, span, string,
   source-file, ...).
2. String/symbol interning.
3. Source-file table and span representation.
4. Item identifier (DefPath form) and monomorphization fingerprinting.
5. Top-level RegseqModel struct.

Q1-Q7 in `architecture.md` already constrain the design space:

- Q2 eager translation: `'tcx` dies at the bridge; RegseqModel is fully
  owned and self-describing.
- Q3 single-level IR: one ID namespace per kind, used uniformly across
  stages.
- Q5 textual MIR-inspired pretty-printer (primary) plus serde JSON
  (secondary).

These constraints rule out roughly 80% of the design space before any
prior-art reading. The research below confirms what falls out of those
constraints and isolates the residual sub-decisions.

## Methodology

Four parallel research surveys, each focused on a cluster and asked to
report along the same five axes (IDs, interning, spans, item paths,
top-level container) plus a fit-for-Regseq judgment given Q1-Q7.

- Cluster A (rustc internals + rustc_public): general-purpose agent over
  the pinned rustc-src checkout.
- Cluster B (Rust-to-C compilers): explore agent over
  `prior-art/rustc-codegen-c.md`, `rustc-codegen-clr.md`, `mrustc.md`,
  `c2rust.md`.
- Cluster C (Rust verification IRs): explore agent over
  `prior-art/charon.md`, `kani.md`, `creusot.md`, `prusti.md`,
  `verus.md`, `rust-stainless.md`, `mirai.md`.
- Cluster D (general IR design): explore agent over `prior-art/llvm-ir.md`,
  `mlir.md`, `compcert.md`.

Synthesis is mine; per-cluster findings condensed to the parts that bear
on stage-1 vocabulary. Per-project files in `prior-art/` remain the raw
evidence.

## Findings by cluster

### Cluster A: rustc internals and rustc_public

rustc represents IDs as per-kind newtype indices generated by
`rustc_index::newtype_index!`. Each is a `u32` underneath with the top 256
values reserved for niche-tagging (so `Option<Symbol>` is 4 bytes). The
`Idx` trait provides the common interface; `IndexVec<I, T>` is the
canonical dense storage.

`Symbol(SymbolIndex)` is interned through a `Lock<InternerInner>` in
session globals (TLS-scoped). Strings and byte-strings share one index
space. `Symbol::as_str` returns a reference whose lifetime is "lied
about" via transmute, sound only because the arena outlives all callers.

`Span` is bit-packed into 8 bytes with four layouts decoded by tag bits;
`SpanData` is the decoded form `{ lo: BytePos, hi: BytePos, ctxt, parent }`
where `BytePos(u32)` is a global byte offset across the entire SourceMap.
Resolution to (file, line, col) goes through `SourceFile::lookup_line`
with a sorted line-starts table plus multibyte-char tables.

`DefId` is `(CrateNum, DefIndex)` — generics are NOT in the DefId; the
monomorphic identity is `ty::Instance<'tcx> = (DefId, GenericArgs<'tcx>)`.
The structured path is reconstructed by walking parent links through
`DefKey { parent, disambiguated_data: { data: DefPathData, disambiguator } }`.
`DefPathHash` is a 128-bit fingerprint stable across runs;
`DefId` deliberately does NOT implement `Ord` to avoid order-dependence in
incremental compilation.

There is no top-level "root struct" — everything is a query on
`TyCtxt<'tcx>`. The bridge crate `rustc_public_bridge` introduces
`Tables<'tcx, B>` holding eight `IndexMap`s (def_ids, alloc_ids, spans,
types, instances, ty_consts, mir_consts, layouts). The public crate
`rustc_public` re-exposes IDs as `(usize, ThreadLocalIndex)` where
`ThreadLocalIndex` is a `PhantomData<*const ()>` ZST that makes the type
`!Send`/`!Sync`. `Symbol` becomes `pub type Symbol = String` (the public
crate's own docs flag this as a placeholder). `Span` becomes a bare
`(usize, ThreadLocalIndex)` with lazy resolution through scoped TLS.

Implications for Regseq: the rustc-internal idiom (`newtype_index!`-style
typed IDs, `IndexVec`, content-hashed interner, `(DefId, GenericArgs)`
instance identity) is directly transferable. The rustc_public re-shape
serves a different posture (lazy callbacks for an external API surface
that outlives the compilation) and is explicitly ruled out by Q2.

### Cluster B: Rust-to-C compilers

The four projects sampled differ widely. `rustc_codegen_c` and
`rustc_codegen_clr` are codegen backends inside rustc that inherit
monomorphization from `rustc_codegen_ssa` and emit through pretty-printers
operating on lightweight value enums (`CValue::{Scalar, Local, Func}`);
both keep a single owned root (`ModuleArena`) but say little about the
five stage-1 axes — the IR is small and ID schemes are not foregrounded.
mrustc reimplements the entire pipeline in C++ with its own arena/RAII;
no Rust-shaped ID convention to lift. c2rust is C-to-Rust (opposite
direction); its `Translation` context-object pattern is a useful
top-level-shape precedent but its IDs (`CDeclId`, `CTypeId`, `CExprId`)
are clang-AST keys, not Rust-shaped.

The strongest single lesson from this cluster is `rustc_codegen_clr`'s
"one IR, two printers" pattern — about a 2-3 KLOC delta to add a second
backend on top of a shared owned IR. This is direct precedent for
RegseqModel feeding both Linux and Zephyr backends without IR forking.

The cluster does not contradict any of the rustc-internal idioms; it
mostly confirms two-crate splits, single owned roots, and printer
separation. Its silence on interning, span representation, and DefPath
form is itself a signal: at the codegen-replacement scale these are
inherited from rustc and not re-litigated. Regseq, going through
`Callbacks` and producing an owned IR rather than replacing codegen, has
to make those choices explicitly.

### Cluster C: Rust verification IRs

The verification-IR cluster splits cleanly along the monomorphization
axis. Charon and Kani consume MIR post-monomorphization (or with optional
monomorphization); the rest (Creusot, Prusti, Verus, rust-stainless,
MIRAI) preserve generics in the IR because reasoning at the polymorphic
level is essential to verification.

For Regseq's posture (eager monomorphization per Q2; codegen-driven, not
verification-driven), Charon is the closest precedent. Its ULLBC/LLBC are
fully owned, serde-backed, no `'tcx`, with generics preserved as
`GenericParams` but a `--monomorphize` flag that bakes them. Span tracking
is span-by-value through `ErrorCtx`; identifiers are not foregrounded as
a custom newtype scheme in the summary. `serde_state` (a serde extension
that lets the IR own its own interning state during serialization) is an
interesting wrinkle but adds complexity Regseq does not need.

Kani is the second-closest because of its post-mono extraction posture,
but Kani has *no custom IR* — it emits CBMC GOTO programs directly, so
its lessons are about extraction strategy (Stable MIR, CodegenBackend
integration) rather than vocabulary.

The verification-IR family teaches three things worth carrying over:

1. *Owned post-extraction.* Convergent: every project that defines an IR
   makes it owned (Creusot is the only `'tcx`-borrowed exception, and it
   pays for that decision in lifetime complexity throughout the codebase).
2. *Spans are first-class everywhere.* Either inline or carried via
   context; never opaque or external.
3. *Generic-preservation vs eager-monomorphization is a posture choice,
   not a technique choice.* Each side works; Regseq has chosen
   eager-mono in Q2.

What NOT to lift from this cluster: Prusti's 5-tier IR ladder (Q3 single-
level rules this out), Verus's mode system (verification-only), MIRAI's
abstract-interpretation lattice (codegen cannot tolerate Top), Creusot's
`'tcx`-borrowed fMIR.

### Cluster D: General IR design

LLVM uses textual SSA names (`%0`, `@foo`) with `LLVMContext` interning
types and constants; debug info via `!dbg` metadata, not first-class IR
fields. MLIR introduces `Location` as a first-class IR object on every
op/block/value, with extensible dialect machinery and per-dialect bytecode
versioning. CompCert uses bare positive-integer `ident` identifiers and
flat `program` records per-stage IR; nine separate IR types in a layered
ladder with total-function lowerings between them.

Three patterns worth borrowing for Regseq's stage-1:

1. *Owned, context-aware ID representation.* LLVM's `LLVMContext` and
   MLIR's `MLIRContext` both anchor identity for types and attributes. The
   Regseq analogue is a single `RegseqModel` struct hosting tables.
2. *Stable textual form as test contract.* LLVM's `.ll` and MLIR's `.mlir`
   are both designed for FileCheck-style testing. Q5 chose insta over
   FileCheck explicitly, but the design discipline (canonical
   serialization with stable structure, types annotated on every value)
   carries over.
3. *Metadata as side channels.* LLVM's `!dbg`/`!tbaa`/`!prof` keep the op
   set small while carrying domain-specific info inline. The Regseq
   analogue: spans and (later) ISR / register-access tags ride as fields
   on existing variants rather than expanding the core enum vocabulary.

What NOT to borrow: MLIR's open-vocabulary dialect machinery (overkill at
Regseq's scale and contradicts Q3 single-level), bytecode versioning with
AutoUpgrade (Regseq's IR is internal, not an interchange format),
CompCert's per-stage IR types (Q3 already settled).

## Convergent patterns (settled by precedent)

Patterns where multiple clusters agree and the choice is straightforward:

1. *Per-kind newtype IDs, u32 backing.* rustc gives the strongest
   precedent (`newtype_index!` macro; per-kind types like `Local`,
   `BasicBlock`, `SourceScope`; `u32` backing with niche-tagging). Other
   Rust-aware projects show owned/context-indexed representations but are
   not uniform on typed newtypes: Charon inlines IDs in serializable
   structs without a single newtype convention; `rustc_codegen_c` uses
   untyped `CValue::Local(usize)`; c2rust uses Clang-AST keys not Rust-
   shaped IDs; Kani has no custom IR. LLVM/MLIR use symbolic names
   (overkill at our scale); CompCert uses bare `ident` integers (loses
   type safety). Adopt the rustc idiom: hand-rolled `newtype_index!`
   analogue, `u32` backing, `Idx` trait. `NonZeroU32` for fields that
   need niche-optimized `Option<Id>`.
2. *Strong typing all the way down.* rustc keeps newtypes for body-local
   `Local`, `BasicBlock`, `SourceScope`. rustc_public collapses to
   `pub type Local = usize` for consumer simplicity. Regseq is internal;
   typed newtypes for body-local IDs too (`LocalId`, `BlockId`).
3. *Single owned root struct.* Charon's IR crate, codegen_c's
   `ModuleArena`, c2rust's `Translation`, CompCert's `program`, LLVM's
   `Module` -- all single-root. Adopt: `bridge::extract(tcx) ->
   RegseqModel` returns one owned struct.
4. *String interner at the root.* rustc, LLVM, MLIR all intern.
   rustc_public uses `String` directly (acknowledged placeholder). Adopt:
   `StringInterner` at the model root, `StringId(u32)` references
   throughout. Append-only, hash-by-content for serialization stability.
5. *Spans resolved at the bridge boundary.* rustc's bit-packed `Span`
   requires a live `SourceMap`; rustc_public's lazy callback re-enters
   rustc. Q2 explicitly says expand at the bridge. Adopt: `Span`
   carries a resolved `SourceFileId` plus byte offsets; all downstream
   rendering is local.
6. *DefPath as structured data plus rendered string.* rustc has the
   `DefKey` chain (reconstructable but expensive); rustc_public has
   rendered strings only. Both forms are useful for different audiences.
   Adopt: structured `DefPathSegment` list (with disambiguator) plus
   eagerly-computed rendered form on each item.
7. *Generics out of DefId; `Instance = (DefId, GenericArgs)` for
   monomorphic identity.* Universal Rust convention. Adopt: separate
   `ItemId` (per-DefId) from `InstanceId` (per `(ItemId, GenericArgs)`).

These patterns are not relitigated below; they are the floor on which
F1-F4 sit.

## Stage-1 sub-decisions

Four residual forks where the prior-art does not unilaterally pick.
Each is locked here with the rationale and the rejected alternative.

### F1. Span byte representation

**Decision**: byte-offset. `Span { file: SourceFileId, lo: u32, hi: u32 }`,
12 bytes, `[lo, hi)` end-exclusive convention. Pretty-printer resolves
line/col through `SourceFile.line_starts` (binary search).

### Rationale

Three forms were considered: byte-offset (12 B), pre-resolved line/col
(approximately 16 B), and both (24 B).

Byte-offset is the rustc and Charon convention. The pretty-printer holds
`SourceFile` in hand and binary-searches `line_starts` cheaply at print
time. JSON consumers who walk the serialized tree have `line_starts` in
the embedded `SourceFile` table, so they can resolve byte to line/col on
demand without the IR pre-resolving for them.

Byte-offset gives source-text slicing for free (`content[lo..hi]`), which
is useful for diagnostics, the future `analysis` emit spec, and anything
that wants to quote source. Pre-resolved makes that awkward: reverse-
mapping line+col back to a byte range is doable but redundant when the
byte range is the natural primitive.

Multi-byte / display-col handling (rustc's `multibyte_chars` /
`non_narrow_chars`) is needed regardless of which form is stored;
byte-offset just defers the work to render time, which is fine at our
scale.

### Rejected alternatives

- *Pre-resolved (line/col) only.* Slightly larger, complicates
  source-slicing, no convention precedent.
- *Both forms.* Costs 24 bytes per span for a saved binary search per
  render. Not justified at our span density.

### Subordinate notes

- *File-local byte offsets.* `lo` and `hi` are byte offsets into the
  `SourceFile`'s `content` buffer (file-local), not the rustc-internal
  `BytePos` form. rustc's `BytePos(u32)` is a global offset across the
  entire `SourceMap`, with each `SourceFile` carrying a `start_pos` to
  translate. The bridge resolves rustc spans to file-local offsets at
  construction by subtracting `SourceFile.start_pos`. Validation: when
  `SourceFile.content` is `Some(_)`, `[lo, hi)` must satisfy `lo <= hi`
  and `hi <= content.len()`; the bridge can assert this with a clear
  error if rustc ever surfaces a span that does not resolve cleanly.

### F2. Span placement

**Decision**: inline. IR nodes that carry a span carry `Span` by value.
No `SpanId` table.

### Rationale

Sharing factor for source spans across MIR statements is realistically
2-3x, not 10x. At driver-crate scale (O(10^4) spans times 12 bytes,
roughly 100-200 KB), interning would save tens of KB -- negligible for
in-process compilation.

Inline storage matches Charon's convention and keeps construction simple
(no `HashMap<Span, SpanId>` in the bridge, no per-span hashing).
Per-node JSON inlines spans, which is more readable for the
goldenC-authoring workload.

A future canonical-IR equality use case (e.g., bit-identical equality for
incremental caches) would prefer interning, but no such use case exists
today and the migration `inline -> interned` is mechanical.

### Rejected alternatives

- *`SpanId(u32)` interned table.* The space saving is real but small;
  the cost is construction-time hashing and a less-readable per-node JSON
  shape. If snapshot dumps grow uncomfortable, the textual pretty-printer
  can elide spans selectively without changing storage.

### Subordinate notes

- *Reconciliation with Q2.* Q2 originally listed `SpanId` among
  RegseqModel's internal IDs and showed `spans: HashMap<Span, SpanId>`
  in its bridge Tables example (`architecture.md` Q2, subordinate
  decision a, "Internal IDs"). F2 supersedes that for spans
  specifically; `architecture.md` has been amended to drop the
  `SpanId` references. The Q2 pattern (rustc-side handles intern to
  RegseqModel-owned IDs at the bridge) still holds for the other IDs
  Q2 listed (`ItemId`, `TyId`, `BodyId`, `ConstId`, `StringId`,
  `SourceFileId`).
- *Bridge transient state.* The bridge may keep a transient
  `HashMap<rustc::Span, RegseqSpan>` during construction for
  resolution caching (resolving a rustc `Span` to a RegseqModel
  `(SourceFileId, lo, hi)` is a `SourceMap` lookup). That cache is
  an implementation detail of the bridge and is not visible in the
  IR -- the IR-side shape is inline `RegseqSpan` everywhere a span
  appears.

### F3. Source content

**Decision**: hybrid. `SourceFile { path: StringId, content:
Option<Arc<str>>, line_starts: Vec<u32> }`. The bridge populates
`content` for crates Regseq extracts (the spec crate, the `regseq`
facade, any regseq-aware crate). Content is `None` for upstream-crate
sources whose spans surface diagnostically but whose source text we do
not own.

### Rationale

The Q2 self-describing rule (no operation should require reaching back
to rustc or to the filesystem) eliminates path-only storage:
pretty-printing a span without content requires either reading the file
at print time (filesystem dependency) or shipping with no source-line
highlight (degraded output).

Content embedding has a natural scope. Per the `core`-is-opaque
methodology, we do not render `core` MIR; spans into `core` exist (e.g.,
from the `?` desugar) but we never need to display `core`'s source line.
"Crates we extract" is the right boundary, not "every file rustc
references."

`line_starts` must be computed regardless (per F1). Computing it requires
reading the file once at the bridge. Once read, embedding adds no bridge-
time cost -- only IR/JSON size.

### Rejected alternatives

- *Always embed (strict A).* Pulls in upstream-crate source for spans we
  never render in detail. No benefit, real cost.
- *Path-only (strict B).* Violates the Q2 self-describing rule.

### Subordinate notes

- *`Arc<str>` over `String`.* Cheaper to clone (multiple parts of the
  bridge or pretty-printer may hold references). Matches rustc's
  `SourceFile.src: Option<Arc<String>>` convention modulo the inner
  `String`-vs-`str` choice (rustc chose `String` for historical reasons;
  `Arc<str>` is the cleaner default for new code).
- *JSON dump size mitigation.* If embedded content makes JSON dumps
  uncomfortable in practice, add a `--no-source` flag on the `model`
  emit spec at that point. Not a stage-1 concern.
- *Path representation.* Whether `path` is absolute, relative-to-crate-
  root, or rustc-remapped (via `--remap-path-prefix`) is deferred to the
  construction-time spec. Default instinct: store the path as rustc gives
  it after remap, so reproducible-build flags carry through.

### F4. ItemId determinism

**Decision**: sequential `ItemId(u32)` payload plus a side
`IndexVec<ItemId, DefPathHash>` table at the model root. Items are
sorted by structured DefPath (segments plus disambiguator) before
assignment.

### Rationale

`tcx`-iteration order is non-deterministic across incremental builds (the
reason rustc deliberately removes `Ord` from `DefId`). Naive sequential
assignment would cause snapshot tests to flap on the same source between
runs. Sorting at construction fixes this for any sequential scheme.

Three candidate shapes were considered:

- *A: sequential `u32`* alone. Within-build stable. Cross-build identity
  (same DefPath in two different builds maps to the same ID) requires a
  side channel.
- *B: `DefPathHash(Hash128)`* directly. Cross-build stable. 16 bytes per
  reference; noisy in dumps.
- *C: sequential `u32` plus side `DefPathHash` table.* Within-build clean
  IDs, cross-build identity available via the table.

C is the best of both. The cost is one `IndexVec<ItemId, DefPathHash>`
at the model root (`16 * |items|` bytes). Adding the side table later is
mechanical, but `DefPathHash` carries genuine cross-build value: two
RegseqModels for the same source produce sequential `ItemId`s that
depend on the reachable set, while a given item's `DefPathHash` is
stable cross-build. This enables diff alignment of the items table
itself across runs (matching a row in build A to a row in build B by
hash, not by index). Note: `DefPathHash` identifies the *path*, not the
item's body content; "did the body change between builds?" is a
distinct question that would need a separate body fingerprint and is
out of scope for stage 1.

This shape mirrors rustc's runtime convention (per-crate `DefIndex` for
hot paths, `DefPathHash` for cross-session stable form), scaled to
Regseq's use case.

### Rejected alternatives

- *A alone.* Defensible (drop the table, add it back if a use case
  appears). The methodology rule "no defensive infrastructure for
  hypothetical future needs" pushes against premature inclusion. Counter-
  argument: `DefPathHash` is not purely defensive; cross-build diagnostic
  value is concrete.
- *B alone.* 16 bytes per reference adds up across the IR. Dump
  rendering becomes hash-noisy. The clean per-build IDs of A/C are worth
  the side table.

### Subordinate notes

- *Sort key.* Sort by `(crate_name: &str, crate_disambiguator:
  StableCrateId, segments: Vec<SegmentKey>)` where `SegmentKey =
  (data_kind: u8 (discriminant of DefPathData), symbol_text: &str,
  disambiguator: u32)`. Three structural points:
  - The crate-level prefix is required because Q6 places items from
    multiple crates into one RegseqModel (the spec crate, the `regseq`
    facade, regseq-aware deps). Without it, identically-named items in
    different crates would collide. `crate_name` orders the dump
    readably; `StableCrateId` is the rustc-blessed tiebreak for the
    pathological case of two crates sharing a name.
  - Symbol comparison must be on string content (e.g., `Symbol::as_str`
    or the `StringInterner::resolve` form), not on `SymbolIndex` /
    `StringId` numeric payloads. Numeric payloads are allocation-order
    and not deterministic across runs (rustc's
    `Symbol::hash_stable` hashes the string content for the same
    reason).
  - Disambiguator inclusion at the segment level matters for multi-
    impl cases (two impls in the same module differ only by
    disambiguator); `def_path_str` does not always render this, so the
    comparator works directly on the structured DefPath.
- *Other ID kinds.* F4 is specifically about `ItemId` because cross-build
  identity is a meaningful concept for items. `TyId`, `ConstId`,
  `BodyId`, `InstanceId`, `SourceFileId`, `StringId` are all sequential
  `u32` by construction order and have no cross-build stable form because
  their identity is structural in context. `BodyId` may be derived from
  `ItemId` (one body per item); that decision is deferred to Stage 11.

## Items deferred to construction-time spec

Sub-decisions that surfaced during F1-F4 walk-through but do not belong
in stage-1 vocabulary:

- *Path representation under `--remap-path-prefix`.* The bridge stores
  paths as rustc reports them (post-remap). Surface in the construction
  spec.
- *Disambiguator-aware DefPath sort comparator.* The exact key encoding
  (and any `def_path_str` vs `def_path_debug_str` decisions) belongs in
  the construction spec.
- *Empty-default `Symbol` interning.* Whether rustc's empty-symbol
  optimization carries over (or whether `StringId(0)` is a sentinel)
  belongs in stage-1 vocabulary itself, not here.
