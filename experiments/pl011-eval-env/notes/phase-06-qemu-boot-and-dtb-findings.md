# Phase 6 QEMU Boot And DTB Findings

## Purpose

This note records the first successful QEMU boot using the project-controlled
kernel and the Buildroot rootfs, plus the initial DTB/UART findings that came
out of that boot.

## Inputs Used

- kernel image:
  `~/regseq-eval/pl011/kernel-src/pl011-arm64-linux/arch/arm64/boot/Image`
- rootfs image:
  `~/regseq-eval/pl011/rootfs-src/buildroot/output/images/rootfs.ext2`

## Working Boot Command

The successful boot used the default QEMU-generated DTB path rather than a
hand-authored custom DTB file.

Concrete command shape:

```bash
qemu-system-aarch64 \
  -machine virt \
  -cpu cortex-a53 \
  -m 1024 \
  -kernel ~/regseq-eval/pl011/kernel-src/pl011-arm64-linux/arch/arm64/boot/Image \
  -append "root=/dev/vda rw rootwait console=ttyAMA0" \
  -drive file=~/regseq-eval/pl011/rootfs-src/buildroot/output/images/rootfs.ext2,format=raw,if=virtio \
  -serial mon:stdio \
  -serial tcp::4321,server,nowait
```

## Boot Result

The boot was successful.

Observed outcomes:

- the kernel reached userspace and ran `/sbin/init`
- the root filesystem mounted from `vda`
- serial console on `ttyAMA0` worked
- the guest reached a login prompt

Guest-side interaction confirmed:

- kernel version matched the project-controlled `v6.18.21` build
- login as `root` with an empty password worked
- the system was usable for post-boot inspection

## PL011 Findings From Boot

The guest exposed:

- `/dev/ttyAMA0`
- `/dev/ttyS0` through `/dev/ttyS3`

The kernel log showed only one PL011 probe:

- `9000000.pl011: ttyAMA0 at MMIO 0x9000000 ...`

No second guest-visible PL011 device appeared during boot.

## DTB Inspection Finding

To inspect the machine DTB actually generated by QEMU, the following dump step
was used:

```bash
qemu-system-aarch64 \
  -machine virt,dumpdtb=virt-original.dtb \
  -cpu cortex-a53 \
  -m 1024 \
  -serial mon:stdio \
  -serial tcp::4321,server,nowait
```

The dumped file was created at:

- `/home/nyengele/virt-original.dtb`

Inspection of that DTB showed only one PL011 node:

```dts
pl011@9000000 {
    compatible = "arm,pl011", "arm,primecell";
    ...
};
```

The `chosen` node also pointed console output at that same node:

```dts
stdout-path = "/pl011@9000000";
```

## Immediate Conclusion

The current QEMU `virt` machine configuration, as used in this experiment, does
not expose a second guest-visible PL011 UART by default.

The extra QEMU serial backend:

- `-serial tcp::4321,server,nowait`

does not by itself create a second guest PL011 device.

This invalidates the earlier working assumption that the current `virt` setup
already provided two guest-visible PL011 UARTs suitable for "console UART" and
"test UART" separation.

## What This Resolves

This phase resolves:

- the first QEMU boot viability question
- the first console-bring-up question
- whether the default machine DTB already contains two PL011 nodes

## Follow-On Result

The follow-on experiment recorded in:

- `notes/phase-07-owned-qemu-second-pl011-strategy.md`

resolved this open question successfully.

The default `virt` machine still exposes only one PL011 by default, but a
patched owned-QEMU path proved that the experiment can obtain:

- `ttyAMA0` on `0x9000000` for the console
- `ttyAMA1` on `0x9040000` as a second guest-visible PL011
